# ootp-analytics

Models for predicting current and future player performance from Out of the Park Baseball data.

## Where to start

- [docs/workflows.md](docs/workflows.md): what each script is for and the steps for the usual jobs (new ratings files, retraining the models, a new league or game version, a new machine).
- [docs/scripts.md](docs/scripts.md): usage, options and outputs of every script.

`files/` is not in git. The trained models are kept in the S3 bucket `ootp-models` with a history of every set: `python scripts/sync_models.py push` after training, `pull` on another machine (needs `aws configure` credentials).

## Setup

Python 3.14 (pyenv virtualenv `ootp-analytics`). Install the requirements file matching your hardware:

| Hardware | Install |
| --- | --- |
| CPU only (default) | `uv pip install -r requirements-cpu.txt --index-url https://download.pytorch.org/whl/cpu --extra-index-url https://pypi.org/simple --index-strategy unsafe-best-match` |
| NVIDIA GPU (CUDA) | `uv pip install -r requirements-cuda.txt` |
| Intel GPU (XPU) | `uv pip install -r requirements-xpu.txt --index-url https://download.pytorch.org/whl/xpu --extra-index-url https://pypi.org/simple --index-strategy unsafe-best-match` |

The device is chosen at runtime by `util/device.py` (CUDA, then XPU, then CPU). Set `OOTP_DEVICE=cpu` (or `cuda`, `xpu`) to override.

To update, edit `requirements.in` (shared) or `requirements-<hw>.in` and recompile, e.g.:

`uv pip compile requirements-cpu.in -o requirements-cpu.txt --index-strategy unsafe-best-match`

## Tests

`python -m pytest` runs the unit tests and the integration cross-checks. The integration tests use the small csv fixtures in `tests/data` (about 4 MB: one Model-Sim dump season and one TGS export season), so they pass on a fresh clone without the large `files/` folder. To rebuild the fixtures from the full files run `python scripts/make_test_data.py`; to run the integration tests against the full files set `OOTP_TEST_DATA=full`.

## Park factors

`OFFAdj` (batters) and `WAAAdj` (pitchers) are park adjusted when a save lists a ballpark ratings csv in `config/saves.toml` (`ballparks = "ballpark_ratings.csv"`, kept in `files/<save>/`; `files/<save>/<season>/ballpark_ratings.csv` overrides it for one season). Without it they equal `OFF` and `WAA`. Columns: `Team Name, Park, PF AVG, AVG L, AVG R, PF HR, HR L, HR R, PF D, PF T, PF`, where 1.000 is neutral and the L / R columns are for left- and right-handed batters.

- `home_share` (default 0.5) is the share of a player's plate appearances / batters faced in his own park; the rest count as neutral.
- Team names in the csv are matched to the save's teams: dump saves use "city nickname" automatically; export saves need a `[<save>.team_names]` table (team abbreviation to csv name); any exception goes in the same table. Teams without a park are logged and treated as neutral.
- Batters: hits, doubles, triples and home runs are divided by the park factor (by batting side), then `wOBAAdj` and `wRAAAdj` are computed against the league mean of the adjusted wOBA, so league `wRAAAdj` sums to 0. New columns `ParkAVG`, `ParkHR`, `ParkD`, `ParkT`, `wOBAAdj`, `wRAAAdj`. `OFFAdj = BSR + wRAAAdj`.
- Pitchers: expected runs use the run factor `PF`; new columns `ParkRuns`, `ExpRA9Adj`; `WAAAdj` still sums to 0 in every usage bucket.

## Fielding

The make-rate fielding columns (`wPM*`, `wRunsPSeason`, `runsPAdj`, `runsPAdjSeason`, `PlayPercentAA`) judge a fielder against the league **inside each BIZ difficulty tier** (R, L, E, U, Z; "I", impossible, is ignored). `PlaysExpected` is what an average fielder at his position makes on his chances, `PlaysAboveExpected` is the difference and `PlayPercentExp` the expected make rate; the league tier rates are written to `<save>-<season>-fielding-tier-rates.csv`. This removes the effect of the staff and park on which kinds of balls a fielder sees (pitcher and batter BABIP ratings were checked and have no measurable effect). Errors in these columns are charged per chance.

The volume columns (`PlayMadeAA*`, `PlayAAASeason`, `runsPSeason`, `runsPNow`, `EAASeason`) count plays per inning, so they also depend on how many balls in play the staff allows (mostly its strikeout rate). `scripts/validate_fielding_ability.py` and `scripts/fielding_attribute_report.py` check how well the values isolate the fielder.

## Ability values for the models

Fielding: `FldRunsSeason` / `FldRunsAdj` (runs: tier-adjusted plays, catcher framing, outfield arm) are the fielding value without the noisy errors; `ErrRunsSeason` / `ErrRunsAdj` are the error charge on its own. Pitching: `WAA` splits into `FIPRuns` (home runs, walks and hit batters, strikeouts against the usage-bucket average, 13 / 3 / -2 weights), `BABIPRuns` (hits on balls in play against the league BABIP; mostly luck and defense, use `BIP` as the weight) and `OtherRuns` (sequencing, unearned runs, defense): `WAA x 10 = FIPRuns + BABIPRuns + OtherRuns`. `scripts/validate_ability_targets.py` reports how repeatable each value is.

## Processing a save

`python scripts/process_seasons.py <save>` reads the raw files of a save (a folder under `files/` with a table in `config/saves.toml`, which sets the source, ratings set and ballpark file) and writes the processed csv files to `files/<save>/<season>/output/`. By default it processes the latest season only; `--season N` does one season, `--start N` runs from N through the latest, `--start N --stop M` runs the range, and `--list` shows the seasons that have data. A failing season is reported and the rest still run (exit status 1). This replaces `dataImport.ipynb`.

## Models

The value models predict, from a player's ratings, his batting, baserunning, pitching and fielding value (runs per 600 PA, per 200 IP or per season). They are trained, evaluated and applied from scripts; the notebooks and the `Hitting/Pitching/Fielding/BSRModel` classes are the old code and stay until `DevModels` and `reports/PredictionMaker.py` are ported.

```
python scripts/train_models.py Model-Sim --start 2046 --stop 2086      # train every model of a save
python scripts/evaluate_models.py Model-Sim --calibration              # scores stored at training, scores on seasons
python scripts/predict_values.py Model-Sim --season 2086               # predicted values of one season to a csv
python scripts/predict_values.py TGS --models-from Model-Sim           # models trained on one save score another
```

- **Training data** is the processed output of a save (`scripts/process_seasons.py`); the ratings set in `config/saves.toml` names the model folder `files/models/<save>/<ratings>/`, one `.joblib` file per model (weights, scaler, feature names, seasons, scores, platoon mix).
- **Models:** batting, pitching FIP part and pitching BABIP part each have a stacked platoon model (`<stream>-split`: value against right- and left-handed opponents, blended with the league's platoon mix of the player's hand) and a plain total model as a fallback; baserunning; one fielding model per position (C, 1B to 3B, SS, LF, CF, RF). The attribute lists and the model family per stream are in `model/domains.py` (`REVIEWED_FEATURES`, `CHOSEN_FAMILY`); every listed rating exists in the dump and in the in-game export, so models trained on a dump save can score an export save.
- **Evaluation** is player-grouped: no player is on both sides of a split, the network stops on validation players taken from the training set only, and `--start/--stop` of `evaluate_models.py` can score seasons the models never saw (train with `--stop 2080`, evaluate 2081 to 2086).
- **Hardware:** the models are small; ridge and boosting run on the CPU and the networks train on the CPU by default (`--device cuda` or `OOTP_DEVICE=cuda` uses a GPU where available; the Intel NPU cannot train PyTorch models and is not visible from WSL). Artifacts are pickles: only load files you trained.
- **Output** of `predict_values.py`: `batting`, `batting_vs_right`, `batting_vs_left` (runs per 600 PA), `baserunning`, `pitching_fip*` and `pitching_runs` (runs per 200 IP), `pitching_babip` (BABIP above league), `fielding_<position>` (runs per season if he played there), and the `_plain` fallbacks.
- **League-relative values** (`<column>_rel`): each value column has a twin with the playing-time weighted mean of that column over the scored league and season subtracted (`model/relative.py`). The raw columns are values against the league the models were trained on. A league that picks players differently (for example human managers who play good defenders at SS, CF, 2B and 3B) has a different average, and the raw fielding values then run high for it (shortstops of a human OOTP 26 league, +22 runs); the `_rel` columns are values against the league being scored. The script prints the shift it subtracted for each column. The shift is about zero for the league the models were trained on.

## Leagues with a different rating scale
Some leagues show ratings on the 1-10 scale (PBL27: everything; Dugout26: speed, stamina and fielding, batting and pitching stay 20-80). A 1-10 rating is a coarser bucketing of the same underlying rating, and where the buckets end differs per rating column. `config/rating-scales/<version>.csv` (from two dumps of one league taken at the same moment, one per scale; `scripts/build_scale_tables.py`) holds how often each 20-80 value is each 1-10 value. `scripts/compare_scale_approaches.py` (see `docs/rating-scale-comparison-*.md`) found that retraining the value models on ratings turned to 1-10 loses about 0.015 (OOTP27) to 0.025 (OOTP26) of R^2 on average, and converting 1-10 up to 20-80 and reusing the 20-80 models loses about twice that, so `scripts/train_models.py <training save> --scales <league>` trains a model set for the league's mix (`files/models/<save>/<ratings>@<league>/`) and the `scales` key of `config/saves.toml` names it. `scripts/detect_rating_scales.py <league>` shows which columns of a league are on which scale. The outlook models stay on the 20-80 scale: a league with a profile gives them the expected 20-80 value of each 1-10 rating. Workflow: `docs/workflows.md`, 2b.

## Updating after new ratings files
`python scripts/update_all.py` refreshes everything that depends on the ratings and statistics files of your human leagues (the saves of `config/update.toml`, latest season of each; about 35 seconds for two saves): the processed output files, the predicted values, the outlook scores and the lists of `config/viewer.toml` as csv files in `output/lists/`. `update_all.py TGS` does one save, `--season N` another season, `--only outlook lists` some steps, `--if-changed` skips saves whose input files have not changed since the last update, `--steps` lists the steps. Set `org` in `config/update.toml` to also write the lists that compare with your roster. Training the models is not part of the update. When a new function or output is added, add its step to `STEPS` in `scripts/update_all.py` so this stays the one command.

## Viewer
`python scripts/run_viewer.py` starts the viewer (http://localhost:8501); a League selector at the left of the top row of every page switches between the saves of `config/update.toml` (the choice follows to the other pages) and each league opens on its own `org`. The screens: The organization overview is one dense screen for your organization (`org` of the first save in `config/update.toml`, Cleveland for TGS) on each player's current value (`value_now`, runs above the league's average starter at the position; offense + baserunning + defense add up to it): the best 20 position players, the best 10 at each position, the best 20 starting and 20 relief pitchers. Its only choice is the organization. The MLB draft page and the IAFA page have the same layout for the draft class and the international amateurs (no organization: they belong to none yet), and a navigation row at the top of every page links the screens. The minor league page has the same layout for players not on the MLB roster, with a Ceiling / Floor switch instead of the current value: the best 90th (or 10th) percentile value within 5 seasons and the best chance of becoming a top-10 (or top-50) player at the position; the time window is gone. The depth chart page draws an OOTP-style field for one organization: the best five at each fielding position and at designated hitter, and the best ten starting and relief pitchers (the MLB roster view has the same lineup as the acquisitions page), built the way a manager would build a team: the best lineup is chosen first with every player at the position where he adds the most given the others (an assignment problem that maximizes the total value, so the second-best center fielder who is better at right field than anyone else plays right field), then the best backups from the players left, and so on; pitchers likewise to starting and relief pitcher; each player once. Choices: the organization, Show (the entire organization, the MLB roster alone, the minor leagues, or one level / team: AAA, AA, A+, A-, R+, R, the International Complex, ...) and Ranked by (current value, or the ceiling / floor of his best season within 10 years); a name in red is over the limits of his level. A Lineup choice (Overall, vs RHP, vs LHP; current values only) shows the hitters against right- or left-handed starting pitchers: a hitter's value against a side is his value now with the batting part swapped for his split (`batting_vs_right` / `batting_vs_left` of the predicted values; fielding and running are the same, the park effect uses the side a switch hitter bats from against that side); the pitchers stay one list. The limits are in `config/saves.toml`, one table per level of a save (`[TGS.levels."AA"]` with `max_age` and `max_pro_years`; 0 = no limit, the default; the years come from the ratings column `PROY`). The data is in `viewer/depth.py`. The level moves page (minor league management) shows, per level of your organization, the players who should move up or down: it reads each player's key ratings (hitters: contact, gap, power, eye, avoid K's, BABIP; pitchers: stuff, movement, control) against all players of his level in the league, the way you read the game's ratings relative to a level; a player who is green in enough of them and would not be at the bottom of the next level is an Up candidate, one who is old for the level with average ratings is an Up candidate too (no stagnating), one over the age or pro-years limit of his level must move, and one who is weak for the level is a Down candidate, but only to a level whose limits he meets. The focus is the better players while they can still develop: a prospect has a ceiling (the 90th percentile of his best season within ten) in the better fifth of the league's minor leaguers of his kind, his development window is what is left until the age where ratings stop growing (hitters 25, pitchers 26, measured in the training leagues of both game versions and set per version in `config/minors.toml`), and the moves of depth players and of players past their window are only listed on request. The rules are in `config/minors.toml` (and can be changed on the page for the session), the age and pro-years limits and the ladder (the order of the level tables of the save, top first; `ladder = false` leaves a level out) in `config/saves.toml`; statistics are not used. The acquisitions page (MLB roster) shows where the starting lineup, rotation and bullpen of your organization are weak against the starters of the league (the best lineup of the MLB players is chosen, one per position, and each starter is placed among the league's starters at his place; a place nobody can play, such as a missing catcher, is the biggest need) and who could upgrade it: your own players who are not starters (internal, the bench and the minor leaguers), players on waivers (claimed with their contract) and free agents (their one-year demand, signability shown), each with the runs of value they add over the starter and what they cost against the budget space of the season (from the `finance` folder of the export, `<save>-<season>-finances.csv`). It also finds the best set of acquisitions that fits the budget space (an integer program: one acquisition per place, each player once). The rules are in `config/acquisition.toml` and can be changed on the page. The needs and candidates use the players' value now. The export columns it reads: `WAIV` (on waivers), `DEM` (demand), `Sign` (signability), `SLR` and `YL` (contract). A **Park-adjusted values** toggle on the pages that show values (organization, minor leagues, draft, IAFA, depth chart, explorer, acquisitions) values every player as if half his games were played in the park of the organization you are viewing (the save's `home_share`, as in the park-adjusted statistics): a hitter's home runs, doubles, triples and hits move with the park factors (the left or right one by the side he bats from; singles are what is left of the hits) at the league's run weights, a pitcher's runs allowed with the park's run factor; fielding and baserunning stay, the chances of being a top-10 or top-50 player are not moved, a `Park` column shows what the park changes. The hitters' neutral-park rates of home runs, doubles, triples and hits come from four small models trained on the training leagues (`scripts/train_models.py <save> --streams park`, `model/park.py`) and written per league by the `park` step of `update_all.py` (`scripts/predict_park.py`, `<save>-<season>-park-rates.csv`); `viewer/parks.py` turns them into runs. On the acquisitions page every team's starters are valued in their own park and the candidates in yours. The toggle is off for all organizations and free agents and for leagues without park factors or park models. Every table of the viewer opens a player's ratings page when you click a cell of his row (the explorer lists, the acquisitions needs, package and candidate tables, the level moves tables); the depth chart, drawn as html, has a list of its players under the filters that does the same. The Rule 5 page prepares the draft: your draft-eligible players (the `R5` flag of the export) with a recommendation to protect them on the 40-man roster, take the risk (low risk: a prospect who is not ready for the majors, so unlikely to be picked) or expose them; the 40-man arithmetic (on it today from the `ON40` flag of the export, open slots, the players you protect, the free agents you plan to sign, how many have to come off); the players with the least to keep them on the 40-man (not starters, no prospects, lowest value) with their contracts; and draft-eligible players of other organizations who would improve your MLB roster. A player is protected when he is a prospect with development left whose ceiling would start for your MLB team (or a top prospect) and he is ready for the majors, or when he is ready and would start now; the rules are in `config/rule5.toml`. A league whose export has no `ON40` flag gets an estimated 40-man (marked on the page). The explorer has many options (list, seasons ahead, sort, players from, positions, age, levels, organization) and an Excel report with the ordered list, a block per position and the filters used. The queries are in `viewer/queries.py`, `viewer/overview.py` and `viewer/report.py`.

## Outlook tables (player development)
`python scripts/build_outlook_tables.py Model-Sim` builds, for a long CPU league, the tables the outlook models of `plans/16-development-models.md` are trained on, in `files/<save>/outlook/` (`players.csv.gz`, `values.csv.gz`; about 2 minutes for all seasons). `model/outlook_data.py` documents the columns.
- **players**: one row per player and season: age, level, entry route (international / high school draft / college draft / other) and entry season, work ethic, intelligence, leadership, the four prone fields, playing time at every level and `time_share` (a proxy for missed time), the gate ratings, and `stay_h1/2/3/5` (still in the league that many seasons later; NaN, never False, when that season is beyond the table).
- **values**: one row per player, season and slot (C, 1B, 2B, 3B, SS, LF, CF, RF, DH, SP, RP): the league-relative value of his ratings at that slot (from the plan 14 models, not from stats or playing time), the rank among the qualified players of the league and the tier (top 10, top 50, rest; the cutoffs scale with the number of teams: 30 teams give ranks 10 and 50).
- Traits come in two forms so that one model can score both file formats: the dump holds numbers (1-200), the in-game export only categories (L / N / H; proneness Iron Man / Durable / Normal / Fragile / Wrecked). `model/formats.py` turns the dump numbers into the export's categories (cut points estimated by matching the export's shares, stored in `config/outlook.toml`; proneness in three levels because Iron Man and Wrecked depend on history), and the export import keeps the categories in `<trait> cat` columns. `python scripts/check_format_parity.py` writes `docs/export-dump-parity.md`, the check of what is in both formats. Adaptability is only in the export. A player is ranked at a position when his key ratings reach the position's minimum, or his potential rating there reaches the potential minimum. The minimums are measured per ratings set (1st percentile of the top-50 MLB starters at the position, floored to a multiple of 5) and kept in `config/outlook.toml`, where they can be edited; `--remeasure-gates` measures them again.

`python scripts/review_outlook.py <save>` (stage 2 of plan 16, about a minute) writes `docs/outlook-diagnostics-<save>.md`: for one game version, how every rating develops with age and what work ethic, intelligence, proneness and missed playing time change (separate low and high tiers; leadership, loyalty and finances as placebos), who stays in the league, the aging of value, the baseline the outlook models must beat, the playing time lost to proneness, and what high school, college and international entrants must reach at entry. The csv tables go to `plans/data/outlook-review/`.

`python scripts/train_outlook_models.py <save>` (stage 3 of plan 16, about 1 hour per game version) trains the outlook models of that version: quantiles of where a player's value is going (floor, median, ceiling), the chance of being a top 10 / top 50 player at a position, of staying in the league and of being available, for 1, 5, 7 and 10 seasons ahead (`TRAINED_HORIZONS` in `model/outlook_models.py`; 2 and 3 were dropped to save training time), plus a career view (the best season within the next 10: its floor, median and ceiling and the chance of ever being top 10 / top 50). Artifacts go to `files/models/<save>/<ratings>/outlook/`; the held-out evaluation to `docs/outlook-model-evaluation-<save>.md`.

`python scripts/predict_outlook.py <save> [--models-from <save>]` (stage 4 of plan 16, about 15 seconds) scores every player of a season with the outlook models of the same game version and writes `<save>-<season>-outlook-slots.csv` and `-outlook-players.csv` next to the other outputs: the floor, median and ceiling of the value and the chance of being a top 10 / top 50 player at each position 1, 5, 7 and 10 seasons ahead (and 2 and 3 in files made before they were dropped) and for the career view (`_h99`), the chance of staying in the league, availability, the injury risk and cost, and a depth flag. It works on dump and export saves (for example `Dugout26 --models-from Model-Sim-26-Std`). Columns: `docs/outlook-columns.md`.

`python scripts/outlook_lists.py <save> --list very_good --slot SS [--org ABBR]` (stage 5 of plan 16) prints the lists of `config/viewer.toml` from the outlook files: the very good players (chance of being a top-10 player at a position), the good ones (11th to 50th), the ordered ranking, the draft class, the IAFA prospects, free agents, trade targets, and how each player compares with your organization's roster (`p_start`, `p_roster`). The queries are pure functions in `viewer/queries.py`, which the viewer of plan 15 will call.

## Documentation

- `docs/derived-ratings.md`: how the derived ratings are made (contact `CON` is half `BABIP` and half `AVK`; movement `MOV` is about 80 % home runs allowed and 20 % `PBABIP`), with the fitted weights per save. Regenerate with `PYTHONPATH=. python scripts/derived_ratings.py`.
- `docs/model-attribute-ranking.md`: which ratings contribute most to each model's value, with the effect of +10 points and +1 standard deviation in runs. Regenerate after retraining with `PYTHONPATH=. python scripts/rating_importance.py`.
- `docs/model-attribute-ranking-ootp26.md`: the same ranking for the OOTP 26 models (`PYTHONPATH=. python scripts/rating_importance.py Model-Sim-26-Std --out docs/model-attribute-ranking-ootp26.md --observations docs/model-attribute-observations-Standard26.md`).
- `docs/ootp26-vs-ootp27-attribute-impact.md`: how the effect of each rating changed between the OOTP 26 and OOTP 27 models, ranked by the size of the change, and how the two model sets value the same ratings. Regenerate with `PYTHONPATH=. python scripts/compare_versions.py` (about 5 minutes).
